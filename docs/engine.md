# Ядро Xray-core

Как byway находит ядро Xray-core, какую версию ставить, как её заменить или
откатить и что делать, если после обновления ядра перестал собираться конфиг
или ядро не помещается в память и на флеш.

Трафик носит Xray-core, byway собирает для него конфиг и ставит перехват. От
версии ядра зависит, какие ключи можно подключить и в каком виде byway пишет
конфиг. Короткая версия этого документа — раздел
[«Версия ядра»](../README.md#версия-ядра) README.

---

## Где byway берёт ядро

Путь к ядру лежит в опции `byway.main.xray_bin`. Обычно источников два:

| источник | путь | кто ставит и обновляет |
|---|---|---|
| выпуск XTLS на GitHub | `/usr/local/bin/xray-ВЕРСИЯ` | установщик byway, затем `byway engine` |
| пакеты OpenWrt (`xray-core`) | `/usr/bin/xray` | `apk` или `opkg` |

Номер версии в имени файла нужен, чтобы два ядра могли лежать рядом и между
ними можно было переключиться одной опцией.

Путь приходит из настроек, а их правит и панель, поэтому byway не запускает
по нему что попало. Файл должен лежать в `/usr/bin`, `/usr/sbin`,
`/usr/local/bin`, `/bin` или `/sbin`, путь — без `..`, имя файла — начинаться
с `xray`, файл — обычный, исполняемый и с заголовком ELF, а первая строка его
`version` — начинаться со слова `Xray`. Имя и заголовок проверяются до
запуска: иначе `xray_bin=/sbin/reboot` перезагружал бы роутер на каждом вызове
byway. Не подошло — byway пишет `путь к движку отклонён: …` и берёт ядро по
умолчанию. Путь вида `/mnt/sda1/xray` поэтому не примется, а симлинк
`/usr/local/bin/xray-…` на такой файл — примется; про USB — в разделе «Флеш».

Если `xray_bin` пуст, консольный `byway` ищет `xray` в `PATH`, затем
`/usr/bin/xray`; служба сразу берёт `/usr/bin/xray`. `/usr/local/bin` в `PATH`
на OpenWrt не входит, поэтому ядро с GitHub указывается явно — установщик
записывает путь сам. Какое ядро в работе, показывает `byway status`, строка
`движок`.

## Какую версию ставить

Установщик спрашивает версию, только если ядра в системе ещё нет. Номер
можно вписать руками или выбрать:

- **проверенная с byway** — по умолчанию. На ней byway проверен целиком, с
  поднятым туннелем и настоящим трафиком. Сейчас это `26.9.30`; её же ставит
  `byway engine tested`.
- **самая свежая, включая предвыпуски** — первый выпуск в списке XTLS
  (`byway engine newest`).
- **самая свежая стабильная** — то, что GitHub отдаёт как `releases/latest`
  (`byway engine stable`).
- **не ставить** — путь к своему ядру указывается потом.

**«Стабильная» у Xray-core отстаёт.** XTLS помечает предвыпуском всё, что новее
`26.3.27`, а `releases/latest` предвыпуски пропускает. Поэтому «стабильная»
сейчас — `26.3.27`, а проверенная с byway — формально предвыпуск. Разница
практическая: часть ключей (`obfs=salamander` у hysteria2, см. таблицу ниже) на
`26.3.27` не собирается.

Источник установщик выбирает сам: сначала GitHub, при неудаче — пакеты
OpenWrt. Если на флеше свободно меньше 25 МБ, GitHub не пробуется. В пакетах
версию определяет ветка прошивки:

| OpenWrt | Xray-core в пакетах |
|---|---|
| 22.03 | 1.8.3 |
| 23.05 | 24.12.31 |
| 24.10 | 25.1.30 |
| 25.12 | 26.3.27 |

У 1.8.3 нет транспорта `xhttp` и поля `host` у `ws` (см. таблицу ниже). Ядро с
GitHub ставится на любую ветку.

### MIPS без блока плавающей точки

XTLS собирает MIPS-версии только для процессоров с блоком плавающей точки
(FPU). У большинства недорогих MIPS-роутеров его нет, и файл с GitHub там не
запускается. Признак — архитектура `mips*` и нет слова `fpu` в
`/proc/cpuinfo`. Установщик проверяет это до загрузки и предлагает только ядро
из пакетов OpenWrt. `byway engine` на таком процессоре сразу отказывает и
советует `apk upgrade xray-core` или `opkg upgrade xray-core`. Версия ядра
здесь — та, что в пакетах вашей ветки.

## `byway engine`: проверка и замена

```sh
byway engine              # есть ли обновление; ниже — файл, версии у XTLS, место и память
byway engine --check      # только ответ, есть ли обновление
byway engine 26.9.9       # поставить эту версию (новее или старее нынешней)
byway engine tested       # проверенная с byway
byway engine newest       # самая свежая, включая предвыпуски
byway engine stable       # самая свежая стабильная
```

Без аргумента и с `--check` ничего не меняется. Первая строка — есть ли версия
новее установленной; если стоит не проверенная, следом — какая проверенная. Без
`--check` дальше идут путь к файлу, самая свежая и стабильная версии у XTLS,
свободное место на флеше и доступная память. Кнопка «Проверить обновление
ядра» на вкладке «Обслуживание» панели зовёт `byway engine --check`. Заменить
ядро можно только из консоли: замена длится дольше, чем панель ждёт ответа.

Номер версии пишется цифрами через точку, без `v`.

### До замены

Замена не начинается и ничего не трогает, если: нет `unzip` или `sha256sum`;
процессор — MIPS без FPU; нынешнее ядро не найдено или не запускается (тогда
ставить установщиком byway — откатываться не на что); доступной памяти
(`MemAvailable`) меньше 40 МБ; другая замена уже идёт.

Архив выпуска (около 14 МБ) скачивается в `/tmp`, то есть в память, и
сверяется с суммой SHA2-256 из файла `.dgst` того же выпуска. Не скачался, нет
`.dgst`, сумма не сошлась или в архиве нет файла `xray` — архив отброшен,
ничего не тронуто. Сверка защищает от битой загрузки, но не от подмены: через
зеркало `.dgst` приходит с того же зеркала, а напрямую посредника и так
отсекает HTTPS до GitHub. Подписей XTLS не выпускает.

Номер версии и архив запрашиваются сначала через локальный прокси-вход byway
(`local_proxy_port`, по умолчанию 1603), затем напрямую. Если GitHub в вашем
списке, а туннель не работает, не выйдет ни так, ни так: резолвер отдаёт для
GitHub подставной адрес. byway тогда советует снять перехват
(`byway plumb off`) и повторить. Замена сама вернёт перехват при перезапуске
службы; если от неё отказались — `byway plumb on`.

Дальше путь зависит от места на флеше.

### Замена рядом

Если на разделе с `/usr/local/bin` свободно не меньше размера нового ядра без
сжатия плюс 5 МБ (около 40 МБ):

1. Новое ядро распаковывается в `/usr/local/bin/xray-ВЕРСИЯ`. Не запускается на
   этом железе — удаляется.
2. Конфиг собирается под новое ядро и проверяется им же (`xray run -test`). Не
   принят — новое ядро удаляется, прежнее работает с прежним конфигом.
3. `xray_bin` переключается, служба перезапускается: туннель пропадает на
   несколько секунд.
4. До 2,5 минуты byway ждёт, что туннель поднялся.
5. Поднялся — прежнее ядро удаляется, если оно `/usr/local/bin/xray-*`. Ядро
   из пакета остаётся: удалить его в обход пакетного менеджера значит оставить
   пакет с дырой. Снять его — `apk del xray-core` или `opkg remove xray-core`.
6. Не поднялся — `xray_bin` и конфиг возвращаются на прежнее ядро, служба
   перезапускается, новое ядро удаляется.

### Замена через память

Места на второе ядро нет — новое не ляжет на флеш, пока там прежнее:

1. Прежнее ядро должно быть `/usr/local/bin/xray-*`. Если оно из пакета,
   замена не начинается (что делать — в «Откат и ручное переключение»).
2. Пока туннель жив, скачивается архив прежней версии — путь назад. После
   остановки службы GitHub может стать недоступен. Не скачался — замена не
   начинается.
3. Служба останавливается: туннель пропадает примерно на минуту. При «Не
   пускать» запрет на это время ставится и держится до подъёма перехвата.
4. Нужна память: размер ядра плюс 20 МБ (около 55 МБ). Мало — служба
   запускается с прежним ядром.
5. Новое ядро распаковывается в `/tmp` и проверяется там: запускается ли,
   принимает ли конфиг. Отказ — служба запускается с прежним ядром.
6. Прежнее ядро удаляется с флеша, новое записывается под своим именем. С
   этого шага назад — только через архив.
7. Служба запускается, до 2,5 минуты byway ждёт туннель.
8. Не поднялся или новое ядро не легло на флеш — прежнее распаковывается из
   архива из шага 2 и запускается.

Если флеш не принял ни новое, ни прежнее, туннеля нет. byway печатает путь к
архиву прежнего ядра в `/tmp` и команду, которой его поставить руками. Архив
живёт до перезагрузки.

### Что значит «туннель поднялся»

Проверка та же, что у автоотката обновления byway: процесс Xray запущен,
таблица nft перехвата на месте, резолвер роутера отдаёт для первого домена из
списков подставной адрес из пула fakeip. При пустых списках доменов третий
признак не проверяется. Четвёртый — связь через сервер: запрос через
прокси-вход (`local_proxy_port`, 1603) к `example.com`, годится любой ответ
HTTP. Его byway проверяет, только если до замены он проходил: недоступный
сервер — не вина нового ядра, и откатывать ядро за это нельзя.

### Без ключа

Служба выключена (`enabled 0`) или ключа нет (ни `node_url`, ни
`node_urls`, ни своего конфига) — проверять на новом ядре нечего. При замене
рядом byway убеждается, что новое ядро запускается на этом железе, переключает
`xray_bin`, удаляет прежнее `/usr/local/bin/xray-*` и пишет `служба не
работает (выключена или нет ключа) — ядро заменено без проверки туннеля`;
служба не перезапускается. При замене через память конфиг по-прежнему
собирается под новое ядро, поэтому без ключа замена останавливается с
`новый движок не принял конфиг` (причина строкой выше — `ключ не задан`), и
служба запускается с прежним ядром. С ключом и выключенной службой ожидание
туннеля пропускается.

`byway update`, проверка раз в 5 минут (`byway watch`) и автообновление ядро
не трогают. Итог замены пишется в системный журнал (`logread -e byway`).

## Откат и ручное переключение

Откат — та же замена на номер постарше: `byway engine 26.3.27`. После удачной
замены прежнее ядро с GitHub удалено, так что вернуться на него можно только
новой загрузкой.

Если два ядра уже лежат рядом, переключиться можно без загрузки:

```sh
uci set byway.main.xray_bin=/usr/local/bin/xray-26.3.27 && uci commit byway
byway gen && /etc/init.d/byway restart
```

`restart` нужен, потому что `uci commit` из консоли службу не трогает.
«Сохранить и применить» в панели вызывает `reload`, а он сверяет запущенный
файл ядра с заданным в `xray_bin` и при расхождении перезапускает службу.

Если ядро из пакета, а места на второе нет: снять пакет (`apk del xray-core`
или `opkg remove xray-core`) и запустить установщик byway заново (раздел
«Установка» в README). Ядра тогда в системе нет, и установщик спросит версию.
Пока ядра нет, нет и туннеля: перехват снимается, роутер ходит в интернет
напрямую. `byway engine` здесь не поможет — ему нужно работающее прежнее ядро.

## Что зависит от версии ядра

Старое ядро незнакомое поле отбрасывает молча, и `xray run -test` такой конфиг
принимает: проверка ядром здесь ничего не ловит. Поэтому byway спрашивает
версию у самого ядра (`xray version`) и в этих местах пишет конфиг иначе или
отказывает заранее:

| версия ядра | что делает byway |
|---|---|
| ниже 1.8.24 | `ws`: Host пишется в `headers`, а не в `wsSettings.host` — у 1.8.3 этого поля нет, и без развилки CDN отвечал бы 404 |
| ниже 1.8.24 | `httpupgrade`: предупреждение, что ядро может не знать транспорт; конфиг собирается |
| ниже 1.8.24 | `xhttp`: отказ |
| ниже 25.8.29 | шифрование VLESS (`encryption=mlkem768x25519plus`): отказ |
| ниже 26.3.27 | `hysteria2`: отказ |
| ниже 26.3.27 | проверка сертификата по отпечатку или имени (`pcs=`, `pinSHA256=`, `vcn=`): отказ |
| ниже 26.3.27 | `allowInsecure=1` (или `insecure=1`) без отпечатка: отказ; с `allow_insecure 1` в настройках пишется в конфиг с предупреждением, что соединение можно подменить |
| 26.3.27 и новее | `allowInsecure=1` без отпечатка: отказ, ядро не даёт отключить проверку сертификата. С отпечатком пишется только отпечаток |
| ниже 26.7.11 | `obfs=salamander` у hysteria2: отказ |
| ниже 26.7.11 | vless и trojan без TLS или reality к публичному адресу: отказ, как у ядра с 26.7.11; `allow_insecure 1` его снимает. Частные адреса IPv4 проходят |
| 26.9.8 и новее | у прямого выхода (`direct`) разрешение имён (`UseIP`) пишется в `sockopt`, а не в `settings`: прежнее поле ядро объявило устаревшим |

Отказ — сообщение с нужной версией и советом `byway engine tested`; рабочий
конфиг не меняется. Отказы по `allowInsecure` и по ключу без TLS называют
вместо этого команду для своего сервера с самоподписанным сертификатом:

```sh
uci set byway.main.allow_insecure=1 && uci commit byway && /etc/init.d/byway reload
```

Опция только в консоли. Ядро с 26.3.27 (для ключа без TLS — с 26.7.11) она не
переубедит.

Если версию определить не удалось (во втором слове ответа `xray version` нет
цифр), byway считает ядро самым новым и пишет конфиг в современной форме.
Старая сборка с нестандартным ответом на `version` получит поля, которые молча
отбросит.

Ещё несколько изменений byway по версии не различает. Их ловит само ядро на
`xray run -test`, а byway объясняет причину:

- vless и trojan без TLS или reality к публичному адресу ядро отвергает с
  26.7.11; частный адрес — исключение. Чинится на сервере: нужен ключ с
  `security=tls` или `reality`. На ядре до 26.7.11 byway отказывает сам (см.
  таблицу выше).
- `h2` (`http`) и `quic` из ядра удалены. byway предупреждает и отдаёт конфиг
  ядру, ядро отвергает его и называет замену — `xhttp`.
- `header` и `seed` у `kcp` свежие версии удалили, сам транспорт остался. byway
  пишет эти поля, только если они есть в ключе, и предупреждает. На `26.3.27`
  они работают, новее — конфиг отвергается.
- wireguard byway всегда запускает внутри процесса ядра (`noKernelTun`). Свежие
  версии по умолчанию поднимают сетевой интерфейс через `/dev/net/tun` и без
  `kmod-tun` отвергают конфиг. Старые версии поле не знают и пропускают.

Предупреждения ядра об устаревшем (`deprecated`, `will be removed`) byway
печатает при сборке строками `движок: …`: так ядро предупреждает об удалении
за версию-другую. Проверить ключ на нынешнем ядре, не трогая рабочий конфиг,
— `byway check 'ССЫЛКА'`.

## После обновления ядра конфиг не собирается

Каждую сборку byway сначала пишет во временный файл и проверяет ядром. Если
ядро её отвергло, рабочий `/etc/byway/config.json` не меняется. `byway gen`
тогда пишет `движок отверг конфиг, черновик остался в
/tmp/byway-config.new.json`, последние строки ответа ядра и, если причина
известна, что с ней делать. После «Сохранить и применить» в панели или
`uci commit byway` то же видно в системном журнале: конфиг не собрался,
работает прежний. `byway engine` такое ядро не оставляет: новое удаляется,
прежнее остаётся.

Работающий Xray от неудачной сборки не перезапускается и продолжает работать
на прежнем конфиге. Хуже, если ядро обновили в обход `byway engine`, например
`apk upgrade xray-core`. При следующем запуске службы (перезагрузка роутера,
`restart`) новое ядро проверяет уже прежний конфиг. Принят — служба
поднимается на нём. Не принят — служба не стартует, перехват снимается. При
`on_failure=closed` (умолчание) то, что шло через VPN, остаётся закрыто;
при `open` идёт в интернет напрямую.

Причину покажет `byway gen`: последние строки — ответ ядра. Если дело в ключе
(нет TLS, `allowInsecure`, удалённый транспорт), откат ядра даёт только
отсрочку: ключ нужно менять на сервере. Если ядро изменило то, что генерирует
byway, — вернуться на версию, на которой работало: `byway engine НОМЕР`. Для
ядра из пакета — откат пакетом либо снять пакет и поставить ядро установщиком.

И [напишите об этом](https://github.com/tomon-one/byway/issues): такое чинится
в byway, а не каждым у себя. Приложите вывод `byway report` (ключа в нём нет)
и последние строки `byway gen`.

## Флеш

Ядро — один файл около 34–35 МБ. На флеше с ubifs, который сжимает файлы, он
занимает около 18 МБ. Архив выпуска при установке и замене лежит в памяти, а
не на флеше.

Установщику нужно 25 МБ свободных на `/overlay`, иначе ядро ставится из
пакетов OpenWrt. Замене рядом — размер ядра без сжатия плюс 5 МБ, около 40 МБ:
сколько сожмёт ubifs, заранее не узнать, поэтому byway считает по несжатому.
Замене через память хватает места, которое освобождает прежнее ядро.

На роутере, где под свои файлы около 40 МБ, одно ядро занимает почти половину,
и второе рядом не встаёт. Там каждая замена идёт через память, с минутой без
туннеля. Если ядро не встало и из пакетов, а свободно меньше 15 МБ, установщик
так и говорит: настройкой это не исправить, нужен роутер с большим флешем или
extroot.

С extroot (корень на USB-накопителе) `/usr/local/bin` оказывается на
накопителе, места хватает на два ядра, и замена идёт рядом. Положить ядро на
отдельно смонтированную флешку и указать к нему путь напрямую нельзя: путь
вне системных каталогов byway не примет. Можно симлинком с именем `xray*` в
системном каталоге: `ln -s /mnt/sda1/xray /usr/local/bin/xray-usb` и
`uci set byway.main.xray_bin=/usr/local/bin/xray-usb`. Флешка должна быть
смонтирована к старту службы, иначе ядра нет.

Обновление прошивки (sysupgrade) сохраняет файлы byway, но не ядро: 35 МБ в
список сохраняемого не кладутся, sysupgrade упаковывает его в память. После
обновления служба сообщит, что ядро не найдено, и подскажет, как поставить.

`byway-uninstall --purge` удаляет все файлы `/usr/local/bin/xray-*`. Ядро из
пакетов OpenWrt и ядро по любому другому пути остаются.

## Память

Xray написан на Go. Без ограничения сборщик мусора Go даёт куче вырасти
примерно вдвое против живых данных. На роутере с 256 МБ памяти Xray доходил
до ~100 МБ, и ядро Linux убивало его по нехватке памяти (OOM). Служба
поднимала его заново, но соединения каждый раз рвались — снаружи это
выглядело как «туннель моментами отваливается».

Поэтому служба запускает Xray с переменной `GOMEMLIMIT`. Это мягкий предел: у
порога Go чаще собирает мусор и возвращает память системе. Живые данные он не
режет; если их больше предела, Go просто чаще собирает мусор (не более
половины процессорного времени). Хуже, чем OOM, не будет.

Значение берётся из опции `byway.main.xray_memlimit`:

| значение | что будет |
|---|---|
| не задано | 40 % от `MemTotal`, но не меньше 32 МиБ |
| `0`, `off` или `no` | предел не задаётся |
| в форме Go: `B`, `KiB`, `MiB`, `GiB`, `TiB` | передаётся как есть: `96MiB`, `128MiB` |
| `MB` или `M`, `GB` или `G` | переводится в `MiB` и `GiB`: `128MB` → `128MiB` |
| число без единиц | мегабайты: `96` → `96MiB` |
| прочее | в системный журнал `предел памяти «…» не разобран -- взят авто`, предел — как при незаданном |

На роутере с 256 МБ (`MemTotal` около 234 МБ) авто-значение — `93MiB`, обычный
расход Xray — 30–50 МБ. Без перевода Go не принял бы `128MB`, и движок падал
бы при каждом старте.

```sh
uci set byway.main.xray_memlimit=128MiB && uci commit byway
/etc/init.d/byway reload
```

Предел задаётся при запуске процесса. `reload` сверяет его с окружением
работающего движка и при расхождении перезапускает движок. `byway status`
читает его из окружения работающего процесса, а не из настроек: строка
`память … МБ, предел …` показывает то, что действует на деле.

Замене ядра нужна своя память, сверх предела: 40 МБ доступных до начала, а
при замене через память — размер ядра плюс 20 МБ после остановки службы.
Сколько доступно сейчас, показывает `byway engine` без аргумента.
