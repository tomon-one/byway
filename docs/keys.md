# Ключи и подключение

Документ для того, кто подключает свой сервер: разберёт ли byway ссылку, что из
неё попадёт в конфиг Xray-core и почему ключ может быть отвергнут.

## Как ключ становится конфигом

Ключ — ссылка от сервера целиком: `vless://…`, `hy2://…` и так далее. byway
разбирает её сам, собирает исходящее подключение Xray-core и проверяет
результат командой ядра `xray run -test`. Отказать могут оба. byway — когда
ссылку нельзя разобрать, когда она опасна или когда ядро слишком старое для
этого вида; причину он называет сразу. Ядро — когда собранный конфиг ему не
подходит; byway печатает последнюю строку его ошибки и для частых случаев
добавляет объяснение.

Отвергнутый конфиг рабочий не заменяет, туннель остаётся на прежнем. В панели
после «Сохранить и применить» на вкладке «Основное» придёт «Ключ не принят —
работает прежняя настройка» и вывод сборки.

Имя после решётки (`#Germany`) становится названием подключения, в конфиг оно
не попадает. Если порт в ссылке не указан, берётся 443; у vmess порт всегда из
JSON.

Адрес сервера — IPv4 или имя. Литерал IPv6 (`[2001:db8::1]` в ссылке, адрес с
двоеточием в `add` у vmess) отвергается: «адрес IPv6 в ключе не поддержан: … —
нужен IPv4 или имя».

## Виды ссылок

| вид | схема | что нужно |
|---|---|---|
| VLESS | `vless://` | — |
| Trojan | `trojan://` | — |
| VMess | `vmess://` | — |
| Shadowsocks | `ss://` | — |
| SOCKS5 | `socks://` | — |
| Hysteria2 | `hysteria2://`, `hy2://` | Xray-core 26.3.27 и новее |
| WireGuard | `wireguard://`, `wg://` | — |

В busybox на OpenWrt base64 обычно нет; byway раскодирует base64 сам,
отдельный пакет не нужен.

### VLESS и Trojan

```
vless://00000000-0000-0000-0000-000000000000@example.com:443?type=xhttp&security=tls&sni=example.com&path=/x#Name
vless://00000000-0000-0000-0000-000000000000@example.com:443?type=tcp&security=reality&sni=example.com&pbk=AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA&sid=01ab&flow=xtls-rprx-vision#Name
trojan://PASSWORD@example.com:443?type=ws&security=tls&sni=example.com&path=/t#Name
```

До `@` у vless — идентификатор пользователя, у trojan — пароль (проценты в нём
раскодируются полностью). Параметры — в разделе «Параметры ссылки». `flow` и
`encryption` бывают только у vless. `flow` у trojan byway отбрасывает с
предупреждением «flow=… у trojan Xray-core не поддерживает — пропущен», mux при
этом остаётся включённым.

Без `security=` у vless защита считается `none`, у trojan — `tls`: trojan
задуман поверх TLS, и клиенты этот параметр у него часто опускают. vless без
TLS к публичному адресу ядро с 26.7.11 отвергает (см. «Защита»).

### VMess

```
vmess://eyJhZGQiOiJleGFtcGxlLmNvbSIsInBvcnQiOiI0NDMiLC4uLn0=
```

После `vmess://` — base64 от JSON. Читаются поля `add` и `port` (адрес и порт),
`id`, `aid` (alterId, по умолчанию 0; не число — отказ «aid у vmess — не
число»), `net` (транспорт, по умолчанию tcp), `type` (`http` у tcp, тип
заголовка у kcp; `none` значит, что заголовка нет), `host` (заголовок Host, по
умолчанию адрес), `path` (по умолчанию `/`), `tls` (значение `tls` включает
TLS), `sni` (по умолчанию `host`, затем адрес), `scy` (шифрование VMess: `auto`,
`aes-128-gcm`, `chacha20-poly1305`, `none`, `zero`; иное — отказ), `alpn` и `fp`.
У `net=grpc` имя сервиса берётся из `path` — так его пишут клиенты; без `path`
оно пустое.

Прочие поля не читаются, и предупреждения о них нет.

### Shadowsocks

```
ss://YWVzLTI1Ni1nY206UEFTU1dPUkQ@example.com:8388#Name
ss://aes-256-gcm:PASSWORD@example.com:8388#Name
```

Первая форма — base64 от `метод:пароль`, допускается base64url без добивки
`=`. Вторая — то же открытым текстом, проценты в ней раскодируются полностью.
Разбирается и старая форма, где в base64 завёрнута вся ссылка:
`ss://BASE64(метод:пароль@адрес:порт)#Name`. Адрес отделяется по последней
`@`, так что `@` в пароле законна. Транспорт всегда tcp, защита `none`.

Параметры после `?`, кроме `plugin`, не переносятся, и предупреждения о них
нет.

Плагины (`obfs-local`, `v2ray-plugin`) Xray-core не запускает. Ссылка с
`plugin=` разбирается, плагин отбрасывается, и byway предупреждает: сервер,
который ждёт плагин, не ответит.

### SOCKS5

```
socks://user:pass@example.com:1080#Name
```

Логин и пароль — открытым текстом через двоеточие, могут отсутствовать.
Некоторые клиенты кодируют `user:pass` в base64 (`socks://dXNlcjpwYXNz@…`).
byway такую форму раскодирует.

### Hysteria2

```
hy2://PASSWORD@example.com:8443/?sni=example.com#Name
hy2://PASSWORD@example.com:8443/?sni=example.com&obfs=salamander&obfs-password=OBFSPASS#Name
hy2://PASSWORD@example.com:8443/?sni=example.com&insecure=1&pinSHA256=e3b0c442…b855#Name
```

До `@` — пароль, проценты раскодируются полностью. `sni` по умолчанию — адрес
сервера, `alpn` — `h3`. `obfs=salamander` включает обфускацию, без
`obfs-password` — отказ; другие виды `obfs` отвергаются, в Xray-core их нет.
`insecure` и `pinSHA256` — см. «Защита».

Hysteria2 всегда идёт под TLS, `security` из ссылки игнорируется. `fp` не
пишется: у QUIC отпечатка TLS-клиента нет.

Смены портов нет. Ни `mport=`, ни диапазон в порту (`host:443,20000-30000`,
`host:20000-30000`) настройки hysteria в Xray-core не принимают. byway
предупреждает и подключается к первому порту, поэтому сервер должен слушать и
его.

### WireGuard

```
wireguard://AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA%3D@example.com:51820?publickey=BBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBB%3D&address=10.7.0.2%2F32%2Cfd00%3A%3A2%2F128&mtu=1280&reserved=1%2C2%2C3#Name
wg://example.com:51820?pk=AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA%3D&peer_pk=BBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBB%3D&local_address=10.7.0.2%2F32&keepalive=25#Name
```

Первая форма (как у v2rayN) — закрытый ключ до `@`. Вторая (как у Hiddify) —
всё в параметрах. Разбираются обе.

| поле | имена в ссылке | обязательно | форма |
|---|---|---|---|
| закрытый ключ | до `@`, `privatekey`, `secretkey`, `pk` | да | base64 на 44 знака или 64 hex |
| ключ сервера | `publickey`, `peer_pk` | да | то же |
| общий ключ | `presharedkey`, `pre_shared_key`, `psk` | нет | то же |
| адрес в туннеле | `address`, `local_address` | да | IPv4/IPv6 через запятую, префикс по желанию |
| MTU | `mtu` | нет | 3–4 цифры |
| reserved | `reserved` | нет | три числа через запятую |
| keepalive | `keepalive` | нет | до 5 цифр |

Без `address` ссылка отвергается: ядро подставило бы свой адрес, и сервер не
узнал бы клиента. WireGuard работает внутри процесса Xray-core
(`noKernelTun`), модуль tun и отдельный интерфейс не нужны. Транспорта и TLS у
него нет.

### Чего нет

`tuic://` и `hysteria://` первой версии в Xray-core отсутствуют; byway отвечает
«в Xray-core нет; из похожего есть hysteria2». У HTTP(S)-прокси нет вида
ссылки, а MASQUE и XDRIVE byway по ссылке не разбирает: всё это подключается
через «Свой конфиг». Смена портов hysteria2 и плагины Shadowsocks не
переносятся (см. выше). На любую другую схему — «неизвестный вид ссылки».

## Параметры ссылки

Общие для vless, trojan и socks. Добавки hysteria2 и wireguard описаны выше.

| параметр | что делает | если нет |
|---|---|---|
| `type` | транспорт | `tcp` |
| `security` | `tls`, `reality`, `none` | `none` |
| `sni` | имя сервера для TLS и Reality | адрес сервера |
| `fp` | отпечаток TLS-клиента | `chrome` |
| `alpn` | список через запятую | — |
| `path` | путь у ws, httpupgrade, xhttp, tcp+http | `/` |
| `host` | заголовок Host | адрес сервера |
| `headerType` | `http` у tcp; тип заголовка у kcp | — |
| `seed` | kcp | — |
| `serviceName` | grpc | пусто |
| `mode` | grpc: `multi` включает multiMode; xhttp: режим | — |
| `authority` | grpc | — |
| `extra` | xhttp, объект JSON | — |
| `pbk`, `sid`, `spx`, `pqv` | Reality | — |
| `flow` | vless | — |
| `encryption` | vless | `none` |
| `allowInsecure`, `insecure` | отключение проверки сертификата | — |
| `pcs`, `pinSHA256` | отпечаток сертификата сервера | — |
| `vcn` | имя для проверки сертификата | — |
| `quicSecurity`, `key` | транспорт quic, удалённый из ядра | — |

Параметр не из таблицы в конфиг не попадает, и byway предупреждает:
«параметр ссылки «…» byway в конфиг не переносит». Это не отказ, но стоит
проверить, нужен ли он серверу.

Значения параметров раскодируются целиком: `path=%2F%3Fed%3D2048` (так пишет
ранние данные v2rayN) уходит в конфиг как `/?ed=2048`. Кавычка, обратная косая
и управляющие знаки после раскодирования дают отказ (см. «Подозрительные
ссылки»). Исключение — `extra`: в нём раскодируются только `%2F %3A %2C %20
%3D %26` и скобки с кавычками `%7B %7D %22 %5B %5D`.

## Транспорты

| `type` | что попадает в конфиг | ядро до 1.8.24 |
|---|---|---|
| `tcp`, `raw` | `network: tcp`; с `headerType=http` — маскировка под HTTP с `path` и `host` | — |
| `ws` | путь и Host | Host пишется старой формой, в заголовках |
| `grpc` | `serviceName`, `multiMode` при `mode=multi`, `authority` | — |
| `httpupgrade` | путь и Host | предупреждение |
| `xhttp` | путь, Host, `mode`, `extra` | отказ |
| `kcp` | `header` и `seed`, только если они есть в ссылке | — |
| `hysteria` | версия 2, пароль, salamander | — |

Прочие значения `type`, кроме h2, http и quic (о них ниже), отвергаются:
«транспорт … не поддержан».

**`extra` у xhttp.** Это единственный параметр, который идёт в конфиг объектом
JSON, а не строкой. Скобки и кавычки в нём законны, поэтому проверка на
кавычки к нему не применяется. Взамен byway требует ровно один объект:
значение начинается с `{`, кончается парной `}`, после неё ничего нет. Иначе
`extra` могло бы закрыть `xhttpSettings` раньше времени и переписать соседние
поля, вплоть до адреса сервера и защиты, а `run -test` принял бы результат.
Синтаксис внутри объекта проверяет ядро.

**kcp.** Свежие Xray-core убрали из kcp поля `header` и `seed` (замена —
`finalmask`). byway пишет их, только если они есть в ссылке, и предупреждает.
Отвергнет ядро — конфиг не заменится. Без этих полей kcp собирается и на
свежем ядре. Отдельно byway напоминает, что kcp идёт поверх UDP.

**h2/http и quic** удалены из Xray-core целиком. byway предупреждает, называет
замену (xhttp в режиме stream-one) и собирает конфиг как есть, а свежее ядро
его отвергает. Такой ключ меняется на сервере.

## Защита

### tls

`sni` → `serverName`, `fp` → `fingerprint` (кроме hysteria2), `alpn` →
`alpn`. `pcs` или `pinSHA256` → `pinnedPeerCertSha256` (hex, допускаются `:`
и `,`), `vcn` → `verifyPeerCertByName` (имя хоста).

С 26.3.27 Xray-core не даёт отключить проверку сертификата сервера. На ядре
до 26.3.27 byway держит то же правило сам, но позволяет его снять опцией
`allow_insecure` (по умолчанию не задана). `allowInsecure=1` или `true` (то же
для `insecure`) обрабатывается так:

| ядро | `pcs`/`pinSHA256` или `vcn` в ключе | что делает byway |
|---|---|---|
| до 26.3.27 | нет, `allow_insecure` не задана | отказ с подсказкой, как разрешить |
| до 26.3.27 | нет, `allow_insecure 1` | пишет `allowInsecure` и предупреждает, что соединение можно подменить |
| до 26.3.27 | есть | отказ: отпечаток и имя ядро понимает только с 26.3.27 |
| 26.3.27 и новее | есть | отбрасывает флаг, сертификат проверяется по отпечатку или имени |
| 26.3.27 и новее | нет | отказ: нужен отпечаток в ключе или настоящий сертификат на сервере |

`pcs`, `pinSHA256` и `vcn` сами требуют ядра 26.3.27 и новее.

`allow_insecure` нужна для своего сервера с самоподписанным сертификатом.
Опции нет в панели, только в консоли; она входит в выгрузку `byway export`:

```sh
uci set byway.main.allow_insecure=1 && uci commit byway && /etc/init.d/byway reload
```

На ядре 26.3.27 и новее решает само ядро, опция его не переубедит.

### reality

`sni` → `serverName`, `fp` → `fingerprint` (по умолчанию `chrome`), `pbk` →
`publicKey`, `sid` → `shortId`. `spx` → `spiderX` и `pqv` → `mldsa65Verify`
пишутся, только если есть в ссылке.

### none

С 26.7.11 Xray-core отвергает vless и trojan без TLS или Reality, если сервер
на публичном адресе. На ядре до 26.7.11 так же отказывает byway: «ключ vless
или trojan без TLS к публичному адресу: ключ и трафик видны любому на пути».
Частные адреса (`10/8`, `172.16/12`, `192.168/16`, `127/8`, `169.254/16`)
проходят; имя сервера byway считает публичным адресом. Отказ byway снимает
`allow_insecure 1` (см. «tls»), отказ свежего ядра — нет.

Ключ такой, каким его выдал сервер, и чинится только там. После отказа ядра
byway объясняет: нужен ключ с `security=tls` или `reality`.

### Шифрование VLESS

`encryption=mlkem768x25519plus.…` — постквантовое шифрование VLESS, нужно ядро
25.8.29 и новее. byway проверяет только форму: префикс `mlkem768x25519plus.` и
допустимые знаки. Части значения разбирает ядро. Любое другое значение, кроме
`none`, — отказ; `encryption` не у vless — тоже отказ.

### flow=xtls-rprx-vision

Только у vless. Vision работает поверх голого TCP (`type=tcp` или `raw`) с TLS
или Reality. С другими транспортами ядро конфиг примет, а соединение сломается
в работе, поэтому byway предупреждает. Защиту при этом byway не проверяет. С
любым `flow` мультиплексирование выключается.

## Версии ядра

byway спрашивает версию у самого ядра (`xray version`). Если её не удалось
разобрать, ядро считается свежим.

| что | граница | на ядре ниже границы |
|---|---|---|
| транспорт xhttp | 1.8.24 | отказ |
| транспорт ws | 1.8.24 | Host старой формой |
| транспорт httpupgrade | 1.8.24 | предупреждение |
| шифрование VLESS | 25.8.29 | отказ |
| Hysteria2 | 26.3.27 | отказ |
| `pcs`, `pinSHA256`, `vcn` | 26.3.27 | отказ |
| `allowInsecure`, `insecure` | 26.3.27 | без `allow_insecure 1` — отказ, с ней пишется; с этой версии без `pcs`/`vcn` — отказ |
| `obfs=salamander` | 26.7.11 | отказ |
| vless, trojan без TLS к публичному адресу | 26.7.11 | без `allow_insecure 1` — отказ byway; с этой версии отвергает ядро |
| `header`, `seed` у kcp | свежие версии | пишутся как в ссылке, решает ядро |
| h2/http, quic | удалены | отвергает ядро |

При отказе byway называет установленную версию. Для шифрования VLESS,
hysteria2, salamander и pcs/vcn он печатает и команду обновления
`byway engine tested`, для xhttp советует обновить Xray-core или взять ключ на
ws.

## Подозрительные ссылки

Значения из ссылки уходят в конфиг внутрь строк JSON без экранирования. Ключи
часто приходят из подписок и чужих каналов, которым доверять нельзя. Кавычка в
значении закрыла бы строку и дописала бы в конфиг чужие поля: например,
выключила бы проверку сертификата или подменила адрес сервера.

Поэтому после разбора byway проверяет каждое значение, которое идёт в конфиг,
и отказывает, если в нём есть кавычка `"`, обратная косая `\` или управляющий
знак (перевод строки, табуляция). Управляющие знаки ловятся отдельно: `%0A`
становится настоящим переводом строки, а часть проверок формы смотрит только
первую строку. Отказ называет поле. В честной ссылке таких знаков нет.

Поля, которые идут в конфиг без кавычек или имеют твёрдую форму, сверяются с
образцом: порт (1–65535), `aid` у vmess, ключи и числа wireguard, отпечаток
сертификата, `vcn`. `extra` проверяется как один объект JSON.

## Мультиплексирование

Mux сводит много соединений клиентов в несколько соединений к серверу. Число
потоков на соединение задаёт «Mux» на вкладке «Сеть» (`mux_concurrency`). В
поставке — 8, `0` выключает. Допустимо от 0 до 999; пустое значение — 0,
негодное — тоже 0, с предупреждением.

Mux включается для tcp/raw, ws, httpupgrade и kcp. Не включается для xhttp
(у него свой xmux), grpc (свой multiMode), hysteria2 (свои потоки QUIC),
ключей с `flow` (Vision делит поток сам) и wireguard (у него нет потока). О
каждом таком случае byway говорит при сборке. Второй слой поверх собственного
мультиплексирования только мешает: xhttp с mux сводил весь трафик в одно
соединение и работал медленнее. В свой конфиг mux не дописывается.

## Несколько ключей

Способ подключения — поле «Способ подключения» на вкладке «Основное»
(`conn_mode`).

| в панели | `conn_mode` | что в работе |
|---|---|---|
| Один ключ | `key` | поле «Ключ» (`node_url`) |
| Загрузка из подписки | `sub` | ключ, выбранный из подписки (`node_url`) |
| Несколько, вручную | `selector` | ключ, отмеченный в «Активный ключ» (`node_url`) |
| Несколько, автоматически | `urltest` | все ключи из списка «Ключи» (`node_urls`) |
| Свой конфиг | `outbound` | объект JSON из «Конфиг аутбаунда» (`outbound_json`) |

**Подписка.** Адрес — `https://`, по которому сервис отдаёт список
ключей, чаще всего в base64. Кнопка «Загрузить список ключей» скачивает его,
панель раскодирует и показывает ключи. Виды, которых byway не умеет (`ssr`,
`hysteria`, `tuic`, `warp`), видны, но не выбираются. Строки с другими схемами
в списке не показываются. Все пригодные ключи складываются в список «Ключи»,
поэтому потом можно перейти в режим «Несколько, …» без повторной загрузки.
Скачивание идёт через локальный прокси-вход byway, при неудаче — напрямую;
адрес на сам роутер или в частную сеть отвергается. Подписка по `http://`
не принимается: «подписка по http:// не принимается: ключи в ней может
подменить кто угодно на пути — нужен https://». Сам byway подписку не
обновляет: список берётся в момент нажатия кнопки. В консоли `byway sub АДРЕС`
печатает ответ подписки как есть, без раскодирования.

**Несколько, вручную.** В работе только активный ключ, переключение — в
панели. Остальные ключи списка в конфиг не попадают, если их не использует
направление.

**Несколько, автоматически.** Каждый ключ становится отдельным подключением
(`proxy-0`, `proxy-1`, …). `observatory` ядра проверяет каждое запросом к
`https://www.google.com/generate_204`, балансировщик со стратегией `leastPing`
ведёт трафик через ключ с наименьшей задержкой. Интервал — «Интервал проверки
ключей» на вкладке «Дополнительное» (`probe_interval`), по умолчанию `3m`;
формат — число и `s`, `m` или `h`. Ключ, которому byway отказал при разборе
или при сборке транспорта и защиты (allowInsecure без отпечатка, hysteria2 или
pcs на старом ядре, xhttp на ядре 1.x), пропускается с предупреждением
«ключ пропущен: причина», остальные идут в конфиг. Если не годится ни один
ключ, сборка отказывает и работает прежний конфиг.

**Свой конфиг.** Для того, что byway не разбирает по ссылке: HTTP(S)-прокси,
MASQUE, XDRIVE, нестандартные настройки. В поле вписывается объект исходящего
подключения Xray-core: `protocol`, `settings`, при нужде `streamSettings`.
byway дописывает только `"tag": "proxy"` последним полем: при повторе ключа
ядро берёт последний, так что свой `tag` в объекте ничего не сломает. Название
для строки «Подключение» — поле «Название подключения».

Остального byway в свой конфиг не дописывает:

- Метку на сокет. Ко всем своим подключениям byway добавляет
  `streamSettings.sockopt.mark`, когда включена «VPN для программ на роутере»
  (вкладка «Сеть», включена по умолчанию). Метка отделяет собственные
  соединения ядра от перехвата. В своём конфиге её вписывают сами:
  `"sockopt": { "mark": 4194304 }` внутри `streamSettings`. 4194304 — это
  `0x400000`, значение `self_mark` по умолчанию.
- Мультиплексирование. Нужен mux — он пишется в объект.
- Исключение адреса сервера. В режиме «всё через VPN» адрес сервера из ссылки
  идёт мимо туннеля, иначе туннель замкнулся бы сам на себя. В своём конфиге
  адрес внутри JSON, byway его не знает и предупреждает: адрес сервера не
  должен попасть в списки.

## Направления

Направление — отдельный список доменов и подсетей, который идёт через свой
ключ, а не через основной. Вкладка «Маршруты», блок «Направления», кнопка
«Добавить направление».

Имя направления — латиница, цифры, `_` и `-`; оно же имя файла
`/etc/byway/routes/ИМЯ.lst`. Ключ выбирается по имени после решётки, поэтому
он должен лежать в списке «Ключи» (`node_urls`) и иметь имя. Список «Ключи»
виден в режимах «Несколько, …», загрузка подписки заполняет его сама. В файле
домены и подсети IPv4 вперемешку, по одному на строку, с теми же формами, что
в общих списках (`full:`, `keyword:`, `regexp:`).

Правила направлений стоят перед общими: домен, который есть и там, и там, идёт
через ключ направления. Для его ключа действуют те же правила разбора,
транспорта и мультиплексирования, что и для основного. Направление
пропускается с предупреждением, если список пуст, если ключа с таким именем
нет среди добавленных или если ключу отказано при разборе или сборке
(«направление «…»: ключ не разбирается, пропущено»); остальная сборка
продолжается.

Направление выключается без удаления флагом «Включено» в таблице или
`uci set byway.ИМЯ.enabled=0`. Выключенное пропускается без предупреждения.

В консоли направление — секция UCI типа `route`:

```sh
uci set byway.video=route
uci set byway.video.label='Germany'
uci commit byway
mkdir -p /etc/byway/routes
echo 'example.com' > /etc/byway/routes/video.lst
byway gen && /etc/init.d/byway restart
```

## Проверка ключа без туннеля

Обе команды работают с отдельным конфигом во временном файле и рабочий туннель
не трогают. Без аргумента берётся ключ из настроек (`node_url`).
Предупреждения разбора печатаются выше строки результата.

**`byway check ССЫЛКА`** — разбор и `xray run -test` на собранном
подключении. В сеть не ходит.

```
  xhttp        tls        example.com:443  ПРИНЯТ
```

Транспорт, защита, адрес и итог. При отказе ядра — `ОТВЕРГНУТ`, последняя
строка его ошибки и, где известно, объяснение. Код возврата 0 или 1. В режиме
«Свой конфиг» `byway check` без аргумента проверяет объект из «Конфиг
аутбаунда». Пункт «Вписать ключ» в `byway menu` («Подключение к VPN») выполняет
эту проверку до записи ключа и переключает способ подключения на «Один ключ».

**`byway probe ССЫЛКА`** — одно настоящее соединение через сервер. byway
поднимает отдельное ядро с этим ключом и входом SOCKS на `127.0.0.1:15080`,
ждёт 3 секунды и запрашивает через него `https://api.ipify.org` (до 15 секунд).

```
  xhttp/tls    example.com:443        РАБОТАЕТ  выход 203.0.113.7      0.843210 с
```

Справа — адрес, с которым сервер выходит в интернет, и время запроса. Любой
HTTP-ответ, в том числе 302 или 403, значит, что сервер соединение провёл. Нет
ответа — `НЕ РАБОТАЕТ (код …)` и до двух строк ошибок из журнала ядра. Ядро
отвергло конфиг — «конфиг отвергнут ядром» и причина. Порт и адрес проверки
меняются переменными `PROBE_PORT` и `PROBE_URL`. Без аргумента `byway probe`
берёт объект из «Конфиг аутбаунда» в режиме «Свой конфиг», иначе `node_url`.

**`byway probe --all`** проверяет по очереди все ключи из списка «Ключи»
(`node_urls`): перед каждым строка `ключ N ИМЯ`, в конце `работают N из M`.
Это способ найти мёртвый ключ в режиме «Несколько, автоматически», где
`node_url` в работе не участвует.
